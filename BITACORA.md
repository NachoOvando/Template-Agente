# Bitácora — problemas resueltos

Cada vez que algo se rompe y se soluciona (bug, decisión de diseño que falló, enfoque que resultó peor de lo esperado), se documenta acá. Antes de tocar código en un área, buscar entradas relacionadas por palabra clave.

---

## 2026-09-22 — Alembic autogenerate no importaba `pgvector.sqlalchemy.Vector`
**Dónde:** `alembic/env.py`, `alembic/versions/`
**Problema:** La primera migración autogenerada (`create knowledge_chunks table`) referenciaba `pgvector.sqlalchemy.vector.VECTOR(dim=768)` en la columna `embedding` pero no agregaba el `import pgvector.sqlalchemy` al archivo — la migración generada no era Python válido.
**Causa raíz:** Alembic solo sabe renderizar tipos de SQLAlchemy estándar en el `import` block del script generado. Un tipo custom como `Vector` de la librería `pgvector` no tiene un renderer registrado por default, así que autogenerate lo estampa como repr del objeto sin resolver de dónde importarlo.
**Solución:** Se agregó un callback `render_item` en `alembic/env.py` (pasado a `context.configure()`) que detecta instancias de `Vector` y le indica a Alembic explícitamente qué importar y cómo renderizarlas. Con eso, `alembic revision --autogenerate` genera un archivo correcto sin tocar el `.py` de la migración a mano.
**Regla extraída:** Cuando se agregue un tipo de columna que no sea nativo de SQLAlchemy (pgvector u otro futuro), el fix va en `alembic/env.py` (config de autogenerate), nunca editando el archivo de migración generado — eso rompería la regla de "solo autogenerate".

## 2026-09-22 — `CREATE EXTENSION vector` no puede salir de Alembic autogenerate
**Dónde:** `db-init/001_extensions.sql`, `docker-compose.yml`
**Problema:** La regla no negociable dice "Alembic solo autogenerate, nunca SQL a mano", pero para que el tipo `Vector` exista en Postgres hace falta `CREATE EXTENSION vector` — y autogenerate no detecta ni genera eso: solo compara el metadata de SQLAlchemy contra el esquema existente, no sabe nada de extensiones.
**Causa raíz:** Confundir "nunca SQL a mano" (que aplica a las migraciones de esquema de la app: tablas, columnas, índices) con "cero SQL en todo el repo". Son cosas distintas — habilitar una extensión de Postgres es provisioning de infraestructura, no una migración de esquema versionada por Alembic.
**Solución:** Se movió el `CREATE EXTENSION IF NOT EXISTS vector;` a `db-init/001_extensions.sql`, montado como `docker-entrypoint-initdb.d` en el servicio `db` de `docker-compose.yml`. Corre una sola vez, al inicializar el volumen de Postgres, antes de que Alembic toque la base.
**Regla extraída:** Extensiones de Postgres (pgvector, pgcrypto, etc.) se habilitan en `db-init/`, no en una migración de Alembic. Si se agrega una extensión nueva, el archivo va ahí con un comentario explicando por qué no es una migración.

## 2026-09-22 — Race condition: mensajes concurrentes a la misma sesión se pisaban el estado
**Dónde:** `services/conversation_service.py`
**Problema:** El subagente `tester` (corrido como agente general, ver PROGRESS.md) encontró que dos mensajes casi simultáneos a la misma `session_id` (doble clic, retry del cliente) podían perder el turno anterior completo — no solo el `user_profile`, todo el `AgentState`. Lo reprodujo con `asyncio.gather` contra el `ConversationService` real: el perfil final quedó con `slot_a=None` en vez de `"trekking"`.
**Causa raíz:** `handle_message` hacía `get` → `await self._graph.ainvoke(...)` → `set` sobre un dict plano, sin lock. Entre el `get` y el `set` hay varios puntos `await` reales (extracción estructurada, embeddings, generación) — si dos requests para la misma sesión entrelazan ahí, la que termina último pisa a la que terminó antes. Se agrava porque `get_conversation_service()` es `@lru_cache`: un único `ConversationService` compartido por toda la app, así que el escenario es alcanzable desde un cliente real, no solo un test sintético.
**Solución:** Lock por sesión (`asyncio.Lock` en un `defaultdict`, una entrada por `session_id`) alrededor de todo `handle_message`. Sesiones distintas no se bloquean entre sí — solo se serializan los turnos de una misma conversación, que es el comportamiento correcto de todos modos (un agente no debería procesar dos mensajes de la misma charla en paralelo). Test de regresión: `tests/test_graph.py::test_mensajes_concurrentes_misma_sesion_no_se_pisan`, con un `FakeLLMProvider` con `sleep` para forzar el entrelazado — confirmado que falla sin el lock y pasa con él.
**Regla extraída:** Cualquier estado mutable compartido entre requests (dict, cache, etc.) que se lea y escriba alrededor de un `await` necesita lock o algún mecanismo de exclusión — "es in-memory así que no hay problema de concurrencia" es falso en asyncio en cuanto hay un `await` en el medio.

## 2026-09-22 — Primera corrida contra Gemini real: 3 problemas que los tests con FakeLLMProvider no podían detectar
**Dónde:** `llm/gemini_provider.py`, `config.py`, `graph/nodes.py`
**Problema:** Hasta este punto todo se había probado con `FakeLLMProvider` (sin `GOOGLE_API_KEY` real disponible). Al conseguir una key real y correr el seed + `/messages` end-to-end aparecieron tres problemas que ningún test unitario podía haber atrapado, porque dependen del comportamiento real del SDK/modelo, no de nuestra lógica:
  1. `GeminiProvider.generate()` devolvía `response.content`, que con este modelo puede ser una lista de content blocks estructurados (con thought signatures) en vez de un `str` plano — rompía el contrato de `LLMProvider.generate() -> str`.
  2. `gemini_embedding_model = "models/text-embedding-004"` (el default "de memoria") no existe para esta API key/versión — 404 al llamar `embedContent`. El modelo de embeddings vigente es `models/gemini-embedding-001`.
  3. El system prompt de `generate_response_node` no especificaba variante de español — Gemini respondió con "tinca" (chilenismo), fuera de registro para la persona/tono definidos en el prompt.
**Causa raíz:** Nombres de modelo y contratos de SDK "de memoria"/documentación desactualizada, sin verificar contra la API real — y un guardrail de "español natural" en el prompt que no era lo bastante específico sobre *qué* español natural (rioplatense, no genérico).
**Solución:** `response.text` en vez de `response.content` (normaliza a `str`, confirmado `isinstance` que es subclase de `str`). `gemini_embedding_model = "models/gemini-embedding-001"` + `output_dimensionality=settings.embedding_dimensions` explícito (el modelo soporta múltiples dimensiones vía Matryoshka, hay que pedir la que coincide con la columna `Vector` de Postgres). Prompt ajustado: "español rioplatense/argentino (voseo)... sin regionalismos de otros países hispanohablantes".
**Regla extraída:** `FakeLLMProvider` prueba nuestra lógica (ruteo, merge de slots, guardrails), no el contrato real del SDK del proveedor ni la calidad de la generación. Antes de dar una feature por cerrada que toque `LLMProvider`/Gemini, correr al menos una vez contra la API real si hay una key disponible — no alcanza con la suite en verde. Si en algún momento se agrega otro modelo de embeddings o de chat, repetir esta verificación (nombre de modelo, forma del `.content`, registro del español) en vez de asumir que se comporta igual.

## 2026-09-22 — Frontend React: respuestas de Gemini mostraban asteriscos de markdown literales
**Dónde:** `apps/web/src/App.tsx`
**Problema:** Al migrar el frontend de prueba a React + componentes `message`/`message-bubble` de beUI, las respuestas del asistente que usaban markdown (`**negrita**`, listas) se mostraban como texto plano con los símbolos literales — Gemini genera markdown por defecto, pero `MessageBubbleContent` solo renderiza los `children` tal cual, sin parsear nada.
**Causa raíz:** La burbuja de beUI trae CSS pensado para contenido markdown ya renderizado (estilos para `a`, `code`, `ol`, `ul`, `pre` dentro de `bubbleContentClass`), pero no incluye un parser — asume que quien la usa le pasa HTML/JSX ya resuelto, no un string crudo.
**Solución:** Se agregó `react-markdown` y se usa solo para los mensajes `from === "assistant"` (los del usuario son texto plano, no necesitan parseo). Aprovecha el CSS que la burbuja ya traía en vez de pedirle a Gemini que no use markdown.
**Regla extraída:** Cualquier componente de UI que reciba texto generado por el LLM como `children` (no solo burbujas de chat) necesita decidir explícitamente si ese texto es markdown crudo o texto plano — no asumir. Si se agrega otro lugar que muestre `response` del backend, aplicar el mismo criterio.

## 2026-09-22 — Widget embebible: "process is not defined" al cargar en un sitio de terceros
**Dónde:** `apps/web/vite.widget.config.ts`
**Problema:** El bundle IIFE del widget (`dist-widget/widget.js`) tiraba `ReferenceError: process is not defined` apenas cargaba en la página host, antes de montar nada — el contenedor del widget ni siquiera aparecía en el DOM.
**Causa raíz:** El build normal de la SPA (`vite.config.ts`, modo app) reemplaza `process.env.NODE_ENV` automáticamente como parte del comportamiento default de Vite para apps. El modo librería (`build.lib`, usado para el widget) no aplica ese reemplazo por default — y React lee `process.env.NODE_ENV` en runtime para decidir si correr en modo desarrollo o producción.
**Solución:** Se agregó `define: { "process.env.NODE_ENV": JSON.stringify("production") }` en `vite.widget.config.ts`. Efecto colateral bueno: al quedar la condición estática (no dinámica), Vite pudo hacer dead-code elimination de las ramas de desarrollo de React/motion — el bundle bajó de 1.1MB a ~700KB.
**Regla extraída:** Cualquier build en modo `lib`/IIFE que empaquete React (u otra librería que lea `process.env.NODE_ENV`) necesita el `define` explícito — no asumir que Vite lo hace solo fuera del modo app estándar.

## 2026-09-22 — Widget embebible: panel se renderizaba transparente (sin fondo, sin borde)
**Dónde:** `apps/web/src/widget-entry.tsx`
**Problema:** Con el bug de `process` ya resuelto, el widget montaba y funcionaba, pero el panel del chat se veía completamente transparente — se leían los textos y el input, pero sin fondo blanco, sin borde, sin sombra. El CSS del sitio host (fondo oscuro) se veía "a través" del panel.
**Causa raíz:** shadcn/beUI define los colores del tema en un bloque `:root { --background: ...; --foreground: ...; }` en `index.css`. `:root` es un selector que matchea el elemento raíz del *documento* — dentro de un shadow tree no matchea nada, porque el shadow tree no tiene su propio `:root`. Al inyectar ese CSS tal cual dentro de un `<style>` de un shadow root, todas las custom properties de color quedaban sin definir (`var(--background)` resolvía a nada = transparente), pero como es CSS válido no tiraba ningún error — el bug era puramente visual y silencioso.
**Solución:** Al armar el `<style>` que se inyecta en el shadow root (`widget-entry.tsx`), se reemplaza `:root` por `:host` con `widgetCss.replaceAll(":root", ":host")` — `:host` es el selector correcto para "la raíz de este shadow tree" desde adentro de sus propios estilos. No se tocó `index.css` porque la SPA de página completa (`App.tsx`, fuera de cualquier shadow DOM) sigue necesitando `:root` tal cual.
**Regla extraída:** Cualquier CSS que se inyecte dentro de un shadow root y use `:root` para definir custom properties necesita reescribirse a `:host` — buscar este patrón específicamente si en el futuro se agrega otro punto de montaje con Shadow DOM (ej. un segundo widget, o un preview embebido). Como el bug no tira error de consola, solo se detecta mirando el resultado visual — otra razón para no saltarse el paso de "verlo en el navegador" antes de dar algo por terminado.

## 2026-09-22 — Deploy a InsForge: sandbox no soporta raw-TCP ni gRPC, y retrieve_context perdía el tema real
**Dónde:** `apps/api/src/graph/nodes.py`, infraestructura de deploy
**Problema:** Al desplegar en InsForge (Postgres gestionado + Compute) aparecieron tres cosas:
  1. Esta sandbox no puede conectar directo a Postgres (`psycopg.connect(...)` cuelga) — el proxy de red del entorno bloquea explícitamente "raw-TCP databases".
  2. `compute deploy` en modo source (que corre `flyctl` hablando gRPC con el builder remoto de Fly) falla con `x509: certificate signed by unknown authority` — el proxy tampoco soporta gRPC/HTTP2-only APIs, y el error de certificado es un síntoma, no la causa real.
  3. Ya con el backend desplegado y sembrado, una conversación real de dos turnos (turno 1 menciona el tema; turno 2 solo contesta el slot que faltaba) devolvió contexto genérico no relacionado con el tema real del turno 1 — `retrieve_context_node` embebía solo `state["user_message"]`, que en el segundo turno no repite el tema para nada.
**Causa raíz:** (1) y (2) son limitaciones de red del sandbox documentadas en `/root/.ccr/README.md` ("raw-TCP databases" y "gRPC / HTTP/2-only APIs" no soportados — hay que reportarlas, no bordearlas con hacks). (3) es un bug real de diseño: el flujo de "preguntar el slot faltante → el usuario solo contesta eso" es exactamente el caso donde el último mensaje no contiene el tema de la conversación — ese tema vive en `user_profile`, no en `user_message`.
**Solución:** Para (1): usar `alembic upgrade head --sql` (modo offline, no necesita conexión real) para generar el SQL desde la migración ya autogenerada, y aplicarlo con `insforge db query` (HTTPS a su API, no TCP). Para (2): reportado a InsForge vía `feedback`; workaround: `compute deploy --image <url>` (modo imagen, sin flyctl) con la imagen buildeada localmente (build local también necesitó confiar la CA del proxy, ver `/root/.ccr/README.md` sección docker) y pusheada a GHCR vía un workflow de GitHub Actions (que sí tiene credenciales reales, a diferencia del `GITHUB_TOKEN=proxy-injected` de este sandbox). Para (3): `_build_retrieval_query()` en `graph/nodes.py` arma el texto a embeber combinando los slots ya conocidos del `user_profile` (iterando `model_fields` genéricamente, sin atributos hardcodeados) con el mensaje del turno actual — no solo el mensaje.
**Regla extraída:** Nunca romper la política de red del sandbox (raw-TCP, gRPC) — siempre hay una vía HTTPS alternativa (la API del proveedor) si se busca. Y en el grafo: cualquier nodo que use `state["user_message"]` solo, sin considerar el estado acumulado (`user_profile`), es sospechoso de perder contexto en flujos multi-turno — el mensaje de un turno de "solo contestame el slot" casi nunca repite el tema.
